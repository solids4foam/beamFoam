2. beamFoamCoupled::solve
-------------------------
  /Volumes/OpenFOAM/colmmcalister-v2312/run/moorFV/src/sDoFRGBFvBeam/sixDoFFvBeamSolvers/beamFoamCoupled/beamFoamCoupled.C:56

This replaces both updateAcceleration and the Newmark update in FvBeamNewmark.

- It does NOT call updateAcceleration() or applyRestraints(). It loops over
  the restraints itself:
    * Every restraint except the finiteVolumeBeam is evaluated with
      restrain() at the current state. Its force and moment are added to
      fGlobal/tauGlobal. This makes one explicit "applied load" that also
      includes the weight.
    * The finiteVolumeBeam restraint is skipped and kept aside. Only one is
      allowed.
- It turns the constraint tensors into global axes. rConstraints is in body
  axes, so it computes Q & rC & Q.T().
- It calls beamRestraint->solveMonolithic(body, force, moment, tC, rC, dict).
- It overwrites the motion state with what beamFoam returns:
  centreOfRotation, Q, v, a, pi = J & (Q^T & omega), and tau.
  There is no Newmark step in moorFV and no aRelax.


3. finiteVolumeBeam::solveMonolithic
------------------------------------
  /Volumes/OpenFOAM/colmmcalister-v2312/run/moorFV/src/sDoFRGBFvBeam/sixDoFRigidBodyMotionFvBeam/restraints/finiteVolumeBeamRestraint/finiteVolumeBeam.C:446

On the first call only:
- It builds a bodyDict from the moorFV motion: mass, J, orientation, CoM,
  v, omega, beta, gamma and damping. It then calls
      beam.initialiseRigidBodyEnd(bodyDict, vector::zero)
- This creates a rigidBodyEnd object INSIDE beamFoam, and from then on
  beamFoam owns the body dynamics.
- Gravity is passed as zero because the weight is already in "force".
- It is a fatal error if the CoR is not at the CoM, or on a restart.

On every call:
    setRigidBodyEndConstraints
    -> setRigidBodyEndExternalLoad(force, moment)
    -> beam.evolve()
    -> updateTotalFields()
    -> getRigidBodyEndState(state)
It then writes the force histories and returns state.

Compare the partitioned path: there, restrain() evolves the beam with the
attachment displacement prescribed and returns a force. Here the beam is
handed a load and returns the body's motion.

-------------------------------

- rigidBodyEndMonolithicCoupling()

  equations as residuals in DISPLACEMENT form:
    Translation:
        R_x = m/(beta dt^2) (x - x_pred) + c v(x) - F_ext + Q_b

      body with -Q_b.

Partitioned vs monolithic
-------------------------
Partitioned (FvBeamNewmark)            | Monolithic (beamFoamCoupled)
---------------------------------------+---------------------------------------
updateAcceleration: a = F/m, then      | Other restraints are summed by hand,
applyRestraints()                      | explicitly. The beam is NOT a
                                       | restraint force.
Mooring force from restrain(): the     | The beam and body are solved together
beam is solved with the attachment     | in one Newton system
prescribed                             |
Newmark update of v, pi, then position | Newmark lives in rigidBodyEnd
and Q, in moorFV                       | (beamFoam), using x and the step
                                       | rotation vector theta as unknowns
aRelax acceleration relaxation         | None. moorFV copies the accepted
                                       | state as it is.
Constraints applied in moorFV          | Constraints are projections inside
                                       | the Newton matrix


Things worth knowing
--------------------
- The external load is frozen during the Newton loop. Fluid forces, the
  weight and the other restraints are evaluated once, at the moorFV state at
  the start of solve. Only the beam-body interaction is implicit.
- Angular momentum is rebuilt, not integrated. moorFV's pi is reconstructed
  from beamFoam's omega, and tau holds moment + beamTorque in body axes. That
  is for reporting only and isn't used to advance anything.
- There is one switch between partitioned and monolithic coupling in each
  setting: the moorFV solver type (FvBeamNewmark or beamFoamCoupled), and
  rigidBodyCoupling (partitioned or monolithic) for a beamFoam-only
  rigidBodyEnd. The earlier BlockEigen rigid-body coupling was removed on
  2026-10-20 (see the last section).

Part 1: evolveBeam() (E:55-696)
-------------------------------
evolveBeam is the beam's Newton-Raphson loop for one time step. The unknowns
are the increments DW and DTheta in every cell. Each pass of the
do { ... } while (!checkConvergence(...)) loop assembles the linearised
system, solves it, updates the fields and checks convergence. In monolithic
mode the body is solved inside the same loop.

Step 1: Setup and the Newton loop (E:58-99)
  Reads the tolerances (nCorrectors, residualTol, solutionTol, ...) and
  starts the loop:
      iOuterCorr() = 0;          // E:98
      do                         // E:99

Step 2: Allocate the block system (E:109-136)
  Each cell gets one 6x6 diagonal block d. Each internal face gets one 6x6
  block in l and one in u. Each cell also gets a 6x1 entry in source.
  Rows 0-2 of a cell are its force balance and rows 3-5 its moment balance.
      Field<scalarSquareMatrix> d(mesh().nCells(), scalarSquareMatrix(6, 0.0));
      Field<scalarRectangularMatrix> source(mesh().nCells(), scalarRectangularMatrix(6, 1, 0.0));

Step 3: Newmark predictor for the beam, first iteration only (E:145-173)
      newmarkPredictorTimeIndex_ = runTime().timeIndex();   // E:154
      Accl_ = -(1/(runTime().deltaT()*betaN_))*U_.oldTime() - (0.5/betaN_ - 1)*Accl_.oldTime();

Step 4: Put the body iterate on the attachment boundary (E:175-190).
        Monolithic step A.
      if (rigidBodyEndMonolithic())                      // E:178
      {
          if (runTime().timeIndex() <= rigidBodyEndPtr_().nJacobianChecks() && iOuterCorr() < 2)
          {
              checkRigidBodyEndJacobian();               // E:186, optional FD check
          }
          setRigidBodyEndIterate(rigidBodyEndX_, rigidBodyEndTheta_);   // E:189
      }
  setRigidBodyEndIterate writes W on the attachment face as x + R(theta) r - r0
  and calls W_.storePrevIter(). This makes the boundary increment zero, so
  the beam assembly treats the attachment face as fixed. The body's columns
  in the matrix then carry the motion of that face.

Step 5: Assemble the beam Jacobian and residual (E:192-203)
      W_.boundaryFieldRef().updateCoeffs();          // E:192
      Theta_.boundaryFieldRef().updateCoeffs();      // E:193
      updateEqnCoefficients();                        // E:199
      assembleMatrixCoefficients(d, l, u, source);    // E:203

Step 6: Add loads to source (E:205-551)
  - distributed force q, from E:205
  - line weight rho*A*g*L
  - point forces and moments
  - distributed moment m
  - the beam's own inertia: explicit parts go into source, implicit parts
    onto d (from E:329)
  - run-time momentum contributions such as drag and ground contact
    (from E:517):
        source[cellI](0,0) += linMomSource[cellI][vector::X];
        d += diagCoeff;

Step 7: Create the solver and attach the body (E:556-567).
        Monolithic step B.
      BlockEigenSolverOF eigenSolver(d, l, u, own, nei);         // E:557

      if (rigidBodyEndMonolithic())                               // E:559
      {
          RigidBodyMonolithicCoupling coupling =
              rigidBodyEndMonolithicCoupling();                   // build body rows/cols + residual
          constrainRigidBodyEndCoupling(coupling);                // project onto free DOFs
          eigenSolver.setMonolithicCoupling(coupling);            // E:566
      }
  - rigidBodyEndMonolithicCoupling() evaluates the body residual at the
    current (x, theta) and its Jacobian blocks. It also builds the blocks
    that couple the body to the attachment cell.
  - constrainRigidBodyEndCoupling() applies the moorFV motion constraints.
  - setMonolithicCoupling itself does almost nothing. It is a one-line
    setter in BlockEigenSolverOF.H:154:
        void setMonolithicCoupling(const RigidBodyMonolithicCoupling& coupling)
        {
            monolithicCoupling_ = coupling;
        }
    It stores the struct. The work happens later, inside eigenSolver.solve
    (Part 2).

Step 8: Solve (E:569-580)
      currentResidualNorm = eigenSolver.solve(solVec, source);   // E:575
  - solVec gets the beam increments.
  - eigenSolver.bodyTranslationIncrement() and bodyRotationIncrement() give
    the body's dx and dtheta.
  - The return value is the norm of the full residual, beam plus body.

Step 9: Copy beam increments into DW and DTheta (E:582-598)
      DWI[cellI][vector::X] = solVec[cellI](0, 0);   // E:588
      ...
      DW_.correctBoundaryConditions();               // E:597
      DTheta_.correctBoundaryConditions();

Step 10: Update the body and move the attachment face exactly (E:600-636).
         Monolithic step C.
      const vector dx = eigenSolver.bodyTranslationIncrement();
      const vector dTheta = rigidBodyEndPtr_().rotation() ? eigenSolver.bodyRotationIncrement() : vector::zero;
      rigidBodyEndIncrementSqr = magSqr(dx) + magSqr(dTheta);
      rigidBodyEndX_ += dx;                                                    // E:615
      rigidBodyEndTheta_ += dTheta;
      const vector WbNew = rigidBodyEndAttachmentW(rigidBodyEndX_, rigidBodyEndTheta_);
      DW_.boundaryFieldRef()[patchI][0] = WbNew - W_.boundaryField()[patchI][0];
      W_.boundaryFieldRef()[patchI][0] = WbNew;                                // E:624
  The attachment point comes from the nonlinear map x + R(theta) r - r0, not
  from the linearised increment. A welded joint also turns the end face here.

Step 11: Update fields and check convergence (E:640-695)
      updateSolutionVariables();                                           // E:640: W += DW, Lambda, Q, M...
      deltaXNorm = sqrt(sum(magSqr(solVec)) + rigidBodyEndIncrementSqr);   // E:644: body included
      ...
      while (!checkConvergence(currentResidualNorm, initialResidualNorm, deltaXNorm, XNorm, ++iOuterCorr(), ...));  // E:672
  checkConvergence (E:952) stops the loop when any one of these holds:
  - the residual is at or below the absolute tolerance
  - the residual is at or below residualTol x the first residual
  - deltaXNorm is at or below solutionTol x XNorm
  Because the body is in both the residual and the step norm, the loop only
  stops when the beam and body are converged together.

After the loop, evolveMonolithicRigidBodyEnd calls body.accept(...). That
turns the converged x and theta into a, v, alpha and omega.


Part 2: BlockEigenSolverOF.C
----------------------------
What the file is
  It wraps the Eigen library so it can solve OpenFOAM's 6x6-block beam
  system. There are three parts:
  - The constructor (B:290) stores d, l, u, own, nei.
  - convertFoamMatrixToEigenMatrix (B:44) flattens the blocks into one
    sparse matrix, A.
  - solve (B:312) builds b and x, solves A x = b, and copies the results
    back.

Matrix layout: 6 extra rows only for a monolithic body
  Without a monolithic body the matrix is the beam's alone. With one,
  nBlocks() (BlockEigenSolverOF.H) adds one 6x6 block row and column after
  the beam cells:
      const label nRows = 6*nBlocks();         // B:56
      const label rbRow = 6*d.size();          // first body row
  Rows rbRow..rbRow+2 are the body translation, rbRow+3..rbRow+5 its
  rotation. Without rotation the rotation rows are identity with zero
  right-hand side (B:103-113).

Where the monolithic coupling goes into the matrix (B:97-231)
      if (monolithicCoupling_.active)                       // B:97
      {
          const RigidBodyMonolithicCoupling& c = monolithicCoupling_;
          const label rbRow = 6*d.size();
          const label beamRow = 6*c.attachmentCell;
  For a 3x3 loop over (rowI, colI) it adds:

  Matrix position                          Coefficient            Meaning
  ---------------------------------------  ---------------------  ------------------------------------
  attachment-cell force rows x             beamWRowCoeff (= K_b)  moving the body by dx moves the fixed
    body translation cols                                         attachment face, which changes the
                                                                  force in the end cell
  attachment-cell moment rows x            beamThetaRowCoeff      same effect, on the moment balance
    body translation cols
  body translation rows x                  bodyCoeff              m/(beta dt^2) + ... plus K_b
    body translation cols
  body translation rows x                  bodyWCoeff,            the force the beam puts on the body
    attachment-cell W and Theta cols       bodyThetaCoeff         depends on the end cell
  the same pattern for rotation            beamWRowRotCoeff,      effects through the arm r and the
    (only if rotationActive)               bodyTransRotCoeff,     rotation Jacobian
                                           bodyRotCoeff,
                                           bodyRotWCoeff, ...

  For example:
      coefficients.push_back(Eigen::Triplet<scalar>(beamRow + rowI, rbRow + colI,
          c.beamWRowCoeff(rowI, colI)));             // B:125
      ...
      coefficients.push_back(Eigen::Triplet<scalar>(rbRow + rowI, rbRow + colI,
          c.bodyCoeff(rowI, colI)));                 // B:143

  The full system looks like this:

                    beam cells (6 cols each)                 body (6 cols)
                 +-------------------------------------+----------------------+
       beam rows |  d / l / u  (beam Jacobian)         | only attachment-cell |   [DW,DTheta]   [beam source]
                 |                                     | rows: beam*RowCoeff  | .             =
                 +-------------------------------------+----------------------+
       body rows | only attachment-cell cols:          | bodyCoeff  TransRot  |   [dx, dtheta]  [bodySource,
                 | bodyWCoeff, bodyThetaCoeff, Rot...  | RotTrans   bodyRot   |                  bodyRotSource]
                 +-------------------------------------+----------------------+

  The beam's u and l face blocks are added after that (B:234-279), then
  A.setFromTriplets(...) (B:282).

What solve() does (B:312-540), step by step
  1. Build the matrix and find the first body row:
         convertFoamMatrixToEigenMatrix(d_, l_, u_, own_, nei_, A);
         const label rigidStart = 6*d_.size();   // B:324

  2. RHS b (B:327-354). The beam rows are copied from source. With a
     monolithic body its rows get minus the body residuals:
         if (monolithicCoupling_.active)                              // B:344
         {
             for (label i = 0; i < 3; ++i)
             {
                 b(rigidStart + i) = monolithicCoupling_.bodySource[i];          // -R_x
                 b(rigidStart + 3 + i) = monolithicCoupling_.rotationActive
                   ? monolithicCoupling_.bodyRotSource[i] : 0;                   // -R_theta
             }
         }

  3. Initial guess x (B:357-377). The beam part is copied from foamX, which
     is the zeroed solVec. The body part is set to zero.

  4. Initial residual (B:380-416). This is ||b - A x|| with x = 0, so it is
     just ||b|| over the beam rows and, with a monolithic body, the body
     rows. It is the value evolveBeam uses as currentResidualNorm.

  5. Direct solve (B:419-506). sol is fixed at SparseLU with COLAMD
     ordering, a direct factorisation:
         Eigen::SparseLU<Eigen::SparseMatrix<scalar>, Eigen::COLAMDOrdering<int>> solver(A);
         x = solver.solve(b);                    // B:443
     The BiCGSTAB, GMRES, DGMRES and MINRES cases are not used.

  6. Copy results back (B:509-537). The beam increments go into foamX,
     which is solVec. The body increments are kept for the accessors
     bodyTranslationIncrement() and bodyRotationIncrement():
         bodyTranslationIncrement_[i] = x(rigidStart + i);       // B:529
         bodyRotationIncrement_[i] = x(rigidStart + 3 + i);
     They are increments, which evolveBeam adds on at E:615.

Legacy BlockEigen rigid-body coupling: removed 2026-10-20
=========================================================================

An earlier attempt at coupling the body inside BlockEigenSolverOF, from
before rigidBodyEnd, was removed. It was switched on by
blockEigenKinematicCoupling, blockEigenForceCoupling and
blockEigenKinematicCouplingMode in beamProperties, and by
beamAttachmentKinematics solvedByBlockEigen and
blockEigenAuthoritativeMotion in the finiteVolumeBeam restraint. Those keys
now stop the run with a fatal error.

Removed from beamFoam:
  - RigidBodyState, RigidBodyStepData, RigidBodySolution and
    RigidBodyForceCoupling (RigidBodyCouplingData.H)
  - beamModel::setRigidBodyStepData and getRigidBodySolution, and the
    rigidBodyData_, rigidBodySolution_ and blockEigen* members of
    coupledTotalLagNewtonRaphsonBeam
  - the legacy set-up, sanity checks and attachment override in evolveBeam,
    and the staged attachment source in the boundary conditions
  - BlockEigenSolverOF's legacy constructor, the rigid-body Newmark RHS
    with hard-coded beta and gamma, the kinematic/force coupling blocks and
    the BlockEigenSolve_rigidBodyMotion.dat / force coupling writers. The 6
    body rows are now only added for a monolithic body.
  - tutorials rigidBodyAndBeam/rigidBodyAndBeam, _monolithic (despite its
    name, a legacy case), _ForceCoupledSolver, _fullTime and _shortTime

Removed from moorFV:
  - the RigidBodyStepData packing and the blockEigenAuthoritativeMotion
    branch in finiteVolumeBeam::restrain(), and beamAttachmentKinematics
  - sixDoFRigidBodyMotionFvBeam::applyBlockEigenSolution

The documents BLOCK_EIGEN_RIGID_BODY_COUPLING_PROGRESS.md,
BEAM_ATTACHMENT_KINEMATICS_OWNERSHIP.md,
rigidBodyKinematicCouplingDevelopment.txt and
rigidBodyAndBeamCoupledSolverDevelopmentLog.txt describe that coupling and
are kept as history.
